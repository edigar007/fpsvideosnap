### P2-1：Pipeline stage contract 的 `results` 引用在 checkpoint resume 后可能过期

位置：

- `src/pipeline/pipeline.py:101`
- `src/pipeline/pipeline.py:113`
- `src/pipeline/pipeline.py:193`
- `src/pipeline/runner.py:43`
- `src/pipeline/runner.py:105`

问题：

`Pipeline.__init__()` 在初始化时创建 `PipelineRunner(self._build_stage_contract(), CLIPS_PLAN)`，contract 中的 `results` 字段绑定的是当时的 `self.results` dict。checkpoint resume 时，`_apply_checkpoint()` 直接执行 `self.results = checkpoint.results`。这会让 Pipeline 自身和 context 使用新的 dict，但 runner contract 里的 `stages.results` 仍指向旧 dict。

当前主流程里 `run_full_result()` 不直接使用 `_run_plan()` 的返回值，很多场景不会立即暴露；但 runner 仍在 `target_stage == "metadata"` 和 full tail 返回时读取 `self.stages.results`。这类 stale reference 属于典型的“抽象刚拆出来但状态所有权没完全统一”的风险。

影响：

- resume 后 runner 返回值可能与 Pipeline 当前结果不一致。
- 后续如果有调用方开始依赖 `_run_plan()` 返回的 final video，可能得到 `None` 或旧值。
- contract 单测当前没有覆盖 checkpoint resume 后 results 引用替换。

建议：

1. 不要在 contract 中保存 mutable `results` dict 引用，改为 `get_result(key)` 或 `results_provider: Callable[[], dict]`。
2. 或在 `_apply_checkpoint()` 中使用 `self.results.clear(); self.results.update(checkpoint.results)`，保持 dict identity 不变。
3. 增加回归测试：构造 checkpoint 后加载，断言 `pipeline.runner.stages.results is pipeline.results`，并断言 full plan 返回值与 `pipeline.results[FINAL_VIDEO]` 一致。

### P2-2：Config Assistant 图像测试服务仍复制真实检测链路逻辑，后续容易漂移

位置：

- `src/tools/config_assistant/services/config_test_service.py:37`
- `src/tools/config_assistant/services/config_test_service.py:92`
- `src/tools/config_assistant/services/config_test_service.py:150`
- `src/tools/config_assistant/services/config_test_service.py:351`
- `src/ai/rule_engine.py:35`
- `src/ai/signal_fusion.py:4`

问题：

`ConfigTestService` 自己实现了 `merge_detection_config()`、`calculate_weighted_confidence()`、rule evaluation 和部分 signal boolean 组合。真实检测链路已经有 `DetectionRuleEngine`、`WeightedSignalFusion`、`signals_to_booleans`、`DetectionConfigView` 等模型。当前 Config Assistant 的测试接口虽然运行在单图场景，仍在重复维护“规则合并、权重、信号布尔化”的领域语义。

影响：

- CLI/批处理检测和 Web UI “测试图片”的判断可能在未来配置演进后不一致。
- 新增 detection override 字段时要改两套逻辑，遗漏概率高。
- typed detection view 的收益无法覆盖 Config Assistant 测试服务。

建议：

1. 将 `merge_detection_config()` 迁到共享领域层，或直接复用 `DetectionRuleEngine.merge_detection_config()` 的纯函数版本。
2. 将 `calculate_weighted_confidence()` 改为调用 `WeightedSignalFusion`。
3. 为 Config Assistant 建一个 `DetectionPreviewEvaluator`，输入是已经计算好的 preview signals，规则和权重判断复用 `src.ai` 领域模型。

### P2-3：Dashboard worker 在跨视频 merge 前后缺少细粒度 cancel 检查

位置：

- `src/tools/dashboard/worker.py:230`
- `src/tools/dashboard/worker.py:278`
- `src/tools/dashboard/worker.py:294`
- `src/tools/dashboard/worker.py:296`

问题：

第 4 轮已经把 TaskManager cancel 生命周期显式化，但 worker 侧仍主要在每个视频开始前检查 `cancel_event`。当多个视频都处理完、准备进入 `merge_clips_to_highlight()` 时，代码没有在 merge 前再次检查 cancel；merge 自身也没有接收 cancel token。

影响：

- 用户在 UI 上取消时，如果刚好进入合并阶段，仍可能继续跑完整个 merge。
- TaskManager 最终会终止进程，但 worker 层无法优雅地保存“已处理视频 + 已取消 merge”的结构化状态。
- 长视频、多片段合并时，这会影响 Dashboard 取消体验和诊断。

建议：

1. 在进入 merge 前、merge 后写结果前都检查 `cancel_event`。
2. 给 `merge_clips_to_highlight()` 增加可选 cancel token，至少在 join/audio/report 前后检查。
3. 增加测试：模拟多视频 all_clips 已存在，cancel 在 merge 前置位，断言不会调用 `merge_clips_to_highlight()`。

### P2-4：VideoJoiner 的 FFmpeg 命令构造仍集中在一个类中，后续策略扩展成本高

位置：

- `src/video/video_joiner.py:142`
- `src/video/video_joiner.py:222`
- `src/video/video_joiner.py:253`
- `src/video/video_joiner.py:307`

问题：

`VideoJoiner` 现在已经修正 audio probe 语义，但同一个类仍同时负责：

- ffprobe audio 探测；
- clip normalize；
- silent audio track 补齐；
- concat filter 构建；
- xfade/acrossfade filter 构建；
- encoder 参数选择；
- subprocess 执行和错误处理。

这些职责都在一个 405 行类里，导致后续新增 “无转场快速 concat demuxer”、“软件编码 fallback”、“NVENC 失败降级”、“不同音频策略”等功能时需要继续修改同一个类。

影响：

- FFmpeg 命令测试需要大量字符串断言，脆弱但难以避免。
- 出现 FFmpeg 兼容问题时，定位是 probe、normalize、filter graph 还是 encoder 失败不够直接。
- 不利于针对 concat/xfade/normalize 分别做参数矩阵测试。

建议：

1. 拆出 `AudioProbe`、`ClipNormalizer`、`JoinCommandBuilder`。
2. command builder 返回结构化对象，例如 `FFmpegCommand(args, filter_complex, inputs, outputs)`，测试对结构断言。
3. `VideoJoiner` 保留 orchestrator 职责，只决定策略和调用执行器。

### P3-1：Pipeline facade 仍偏重，stage contract 已拆出但 stage ownership 还未完全下沉

位置：

- `src/pipeline/pipeline.py:112`
- `src/pipeline/pipeline.py:267`
- `src/pipeline/pipeline.py:284`
- `src/pipeline/pipeline.py:304`
- `src/pipeline/pipeline.py:335`

问题：

`PipelineRunner` 不再直接调用 Pipeline 私有方法，这是明显进步。但 Pipeline 自身仍保存大量 stage 具体实现细节：FrameExtractor、YOLO/OpenCV/KillDetector、ClipExtractor、VideoJoiner、AudioMixer、ReportGenerator、HistoryManager 的工厂选择都在 facade 中。

影响：

- 新增 stage 或替换组件仍需要修改 Pipeline。
- stage contract 主要解决 runner 边界，还没有完全解决 stage registry 的执行器注册问题。
- Pipeline 文件仍是最大源码文件，578 行。

建议：

1. 将 metadata/frames/clips 也迁到 `src/pipeline/stages/*.py`，与 join/audio/report/history/cleanup 统一。
2. Stage registry 不只保存 stage order/result keys，也保存 executor factory。
3. Pipeline 只负责 settings/context/checkpoint/component container。

### P3-2：typed config 仍只覆盖 detection 首层，raw dict 读取仍分布较广

位置：

- `src/config/detection_view.py:43`
- `src/ai/kill_detector.py:39`
- `src/ai/signal_extractors.py:148`
- `src/tools/config_assistant/services/config_test_service.py:134`

问题：

`DetectionConfigView` 已覆盖 `confidence_threshold`、`weights`、`rules`、`signals`，但 ROI、OCR、templates、colors、prefilter 等高频结构仍以 raw dict 读取为主。当前属于合理的第一阶段，但下一步需要继续推进。

建议：

1. 增加 `OCRConfigView`、`TemplateConfigView`、`ColorConfigView`、`PrefilterConfigView`。
2. 在 `DetectionSignalExtractor.compute()` 中接受 typed view 或 section view。
3. 对 rule override 后的 effective config 也产出 view，避免 merge 后继续 raw dict 访问。
