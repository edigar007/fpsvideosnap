## 主要发现

### P1：暂无阻断级问题

当前主链路门禁全绿，未发现会立即阻断发布或导致主流程普遍失败的问题。

### P2-1：PipelineRunner 仍依赖 Pipeline 私有方法，拆分边界不够硬

位置：

- `src/pipeline/runner.py:21`
- `src/pipeline/runner.py:29`
- `src/pipeline/runner.py:45`
- `src/pipeline/pipeline.py:267`
- `src/pipeline/pipeline.py:304`
- `src/pipeline/pipeline.py:378`

问题：

`PipelineRunner` 已抽出执行顺序，但它直接调用 `pipeline._run_metadata_stage()`、`_run_detection_stage()`、`_run_join_plan_stage()` 等私有方法。实际边界还是“runner 驱动 Pipeline 内部细节”，而不是“runner 执行 stage contract”。这会让后续新增 stage、替换执行策略、做并行化或测试 runner 时仍必须理解 Pipeline 内部状态。

影响：

- Pipeline 仍是实际的 god facade，当前 495 行。
- runner 单测很难脱离 Pipeline mock。
- stage 的输入输出契约没有完全由类型或注册表表达。

建议：

1. 将 stage 执行封装为 `StageExecutor` 或 `StageDefinition`：`name`、`dependencies`、`run(context) -> StageResult`。
2. `PipelineRunner` 只依赖公开的 stage registry 和 context，不调用 `_run_*` 私有方法。
3. `Pipeline` 保留 facade：负责构造 context、settings、checkpoint store 和组件工厂。

### P2-2：checkpoint 保存不是原子写入，中断可能造成 resume 状态丢失

位置：

- `src/pipeline/checkpoint.py:104`
- `src/pipeline/checkpoint.py:116`
- `src/pipeline/checkpoint.py:119`

问题：

checkpoint 直接 `open(checkpoint_path, "w")` 后 `json.dump()`。如果进程在写入中途被终止、系统断电、磁盘错误或 Dashboard cancel 发生在写入窗口，可能留下半截 JSON。当前 `load()` 会捕获 `json.JSONDecodeError` 并从头开始，这比崩溃好，但会丢失 resume 能力。

影响：

- 长视频处理中断后可能无法复用已完成阶段。
- Dashboard 终止进程时更容易撞上非原子写入窗口。

建议：

1. 使用同目录临时文件写入，例如 `checkpoint.json.tmp`。
2. `json.dump()` 成功并 flush/fsync 后使用 `os.replace(tmp, checkpoint_path)` 原子替换。
3. 保留最近一个 `.bak` 版本，load 当前文件失败时尝试 `.bak`。

### P2-3：Dashboard cancel 仍是强杀进程，状态收敛和资源释放边界偏弱

位置：

- `src/tools/dashboard/task_manager.py:203`
- `src/tools/dashboard/task_manager.py:209`
- `src/tools/dashboard/task_manager.py:212`
- `src/tools/dashboard/task_manager.py:263`

问题：

`cancel_task()` 设置 `cancel_event` 后直接 `terminate()`，再 `kill()`。worker 内部虽然有部分 `cancel_event.is_set()` 检查，但 ffmpeg、OCR worker、checkpoint 写入、临时目录清理等长操作中不一定能优雅退出。`clear()` 也直接丢弃 process/queue 引用，缺少统一的 close/join 过程。

影响：

- Windows 上子进程、ffmpeg 或 PaddleOCR worker 可能残留。
- checkpoint 可能处于半写状态。
- UI 看到 cancelled，但底层资源未必完全回收。

建议：

1. 引入 `TaskRuntime.close()`，统一处理 process join、queue close、monitor thread join。
2. worker 在进入 ffmpeg 前后、每个 stage 前后检查 cancel event。
3. Pipeline stage contract 增加可选 `cancel_checker`，长 stage 主动失败为 `cancelled`。
4. 为 cancel 写 focused test：模拟 worker 长时间运行、cancel 后队列关闭和状态稳定。

### P2-4：Config Assistant 的 config route 仍承担过多配置写入职责

位置：

- `src/tools/config_assistant/routes/config.py:34`
- `src/tools/config_assistant/routes/config.py:76`
- `src/tools/config_assistant/routes/config.py:170`
- `src/tools/config_assistant/routes/config.py:296`

问题：

`api.py` 已成功瘦身为 Blueprint 注册入口，routes 也按主题拆分。但 `routes/config.py` 仍有约 259 行，集中处理 ROI、OCR、templates、colors、export、test-image。它还同时承担 HTTP 参数校验、配置读取、rule override 分支、响应构造。

影响：

- 新增配置项时容易继续堆在同一个 route 文件。
- templates/colors 的 rule override 合并逻辑存在重复模式。
- endpoint 行为和配置写入业务规则仍绑定。

建议：

1. 拆成 `routes/config_core.py`、`routes/config_templates.py`、`routes/config_colors.py`、`routes/config_test.py`。
2. 抽 `ConfigMutationService`，统一：
   - 获取全局或 rule override section；
   - 更新 detection section；
   - 返回更新后的 config；
   - 处理 not found / validation 错误。
3. route 函数只做 HTTP 层：request -> service -> response。

### P2-5：ConfigManagerProxy 依赖 Flask upload folder 推断 manager，属于隐式测试兼容耦合

位置：

- `src/tools/config_assistant/routes/shared.py:9`
- `src/tools/config_assistant/routes/shared.py:14`
- `src/tools/config_assistant/routes/shared.py:21`
- `src/tools/config_assistant/routes/shared.py:29`

问题：

为兼容测试中替换 `api.config_manager` 的行为，`ConfigManagerProxy` 会在 Flask app context 下用 `UPLOAD_FOLDER` 与 manager 的 `project_root` 做 `commonpath` 判断。这个逻辑能工作，但属于隐式推断：配置 manager 的选择不应由 upload folder 路径间接决定。

影响：

- 多 app、多测试或嵌入式使用时，manager 选择行为不够直观。
- 未来改 upload folder 目录结构可能影响 config manager 解析。

建议：

1. 在 `create_app()` 中显式设置 `app.config["CONFIG_MANAGER"] = config_manager`。
2. route 中优先读取 `current_app.config["CONFIG_MANAGER"]`。
3. 测试也通过 app config 注入 manager，逐步移除 `api.config_manager` monkeypatch 兼容层。

### P2-6：VideoJoiner 的音频探测失败语义偏乐观，可能把无音频误判为有音频

位置：

- `src/video/video_joiner.py:101`
- `src/video/video_joiner.py:115`
- `src/video/video_joiner.py:118`
- `src/video/video_joiner.py:245`

问题：

`_has_audio_stream()` 在 ffprobe 任意异常时返回 `True`，日志为 “assuming audio exists”。如果 ffprobe 失败原因不是临时探测问题，而是输入文件无音频、损坏或 ffprobe path 配置错误，后续 concat/xfade filter 会引用 `[i:a]`，FFmpeg 可能在 join 阶段失败。

影响：

- 错误被推迟到更复杂的 filter graph 阶段，诊断成本高。
- 对无音频 clips 的兜底 silent track 可能被绕过。

建议：

1. 将 `_has_audio_stream()` 返回值改为三态：`HAS_AUDIO`、`NO_AUDIO`、`PROBE_FAILED`。
2. `NO_AUDIO` 才走 silent track。
3. `PROBE_FAILED` 应明确失败或进入 conservative normalize 模式，并把 ffprobe stderr 写入 error。
4. 增加 ffprobe path 错误、无音频、损坏输入的单元测试。

### P3-1：检测链路仍有 dict contract 和 typed model 混用

位置：

- `src/ai/kill_detector.py:32`
- `src/ai/kill_detector.py:61`
- `src/ai/signal_extractors.py:17`
- `src/ai/signal_extractors.py:124`
- `src/ai/rule_engine.py:18`

问题：

`KillDetector`、`DetectionRuleEngine`、`DetectionSignalExtractor` 之间主要通过 raw dict 传递 `detection_cfg`、signals 和 rule overrides。虽然已有 `SignalResult`、`DetectionEvent`，但 config 和 rule contract 还没有 typed model。当前代码可用，但后续扩展信号类型、规则 override、阈值策略时仍容易出现字段漂移。

建议：

1. 增加 `DetectionConfigView` / `RuleConfig` dataclass，封装默认值和校验。
2. `DetectionRuleEngine` 接收 typed rules，而不是直接读 dict。
3. `SignalResult` 已有，继续把 `signals` dict 使用范围压缩到模块边界。

## 架构评价

### 已形成的优势

1. Pipeline 有了结构化结果 `PipelineRunResult`，Dashboard/BatchProcessor 不再自行猜测成功失败。
2. checkpoint/resume 和 config fingerprint 已具备基本工程形态。
3. Dashboard worker/progress 与 TaskManager 拆分后，Web 任务生命周期更清楚。
4. Config Assistant 从单文件 API 拆成 routes/services，方向正确。
5. KillDetector 已拆出 rule engine、batch runner、signal extractor，检测逻辑可读性明显提升。
6. offline-only 边界更清楚，`ai.allow_model_download` 默认为 false。
7. 测试覆盖较好，当前质量门禁稳定通过。

### 当前架构短板

1. Pipeline 仍是最核心的复杂度集中点，runner 抽取尚未完全形成独立边界。
2. 配置层 typed settings 只覆盖主链路的一部分，很多模块仍读取 raw dict。
3. Config Assistant HTTP 层和配置写入业务层尚未完全分离。
4. Dashboard 子进程取消与资源释放仍偏命令式，缺少统一 runtime 抽象。
5. FFmpeg 命令构建分散在多个类中，虽然路径配置已统一，但错误模型和 probe 策略还不统一。
