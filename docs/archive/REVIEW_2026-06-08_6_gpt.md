## 是否还有必要继续迭代

结论：不建议再进行“为了提高分数”的大规模整改。

当前项目已经具备较好的工程基本盘：主链路全绿，测试覆盖核心场景，配置驱动边界明确，FFmpeg 和 Pipeline 的主要风险都已经有回归测试。继续追求 9 分以上，很容易变成以下几类过度迭代：

1. 为了降低单文件行数继续拆 Pipeline，但没有新增 stage 或实际替换需求。
2. 为了抽象完整性继续拆 `VideoJoiner` 的 probe、normalizer、executor，但当前 public API 和测试已经稳定。
3. 为了 typed purity 把所有 raw dict 访问都迁到 view，导致配置层和业务层同时维护两套概念。
4. 为了测试数量继续增加 mock-heavy 测试，但只验证实现细节，不提升用户路径信心。

建议进入“维护模式”：只有当真实样本、UI 取消体验、FFmpeg 兼容性或配置编辑流程暴露问题时，再做小范围整改。

## 主要发现

### P1：暂无阻断级问题

当前全量门禁通过，未发现会阻断主流程、测试或发布的系统性缺陷。

### P2-1：Dashboard merge 取消只能在 merge 前后生效，不能中断 merge 内部步骤

位置：

- `src/tools/dashboard/worker.py:282`
- `src/tools/dashboard/worker.py:304`
- `src/tools/dashboard/worker.py:305`
- `src/pipeline/multi_video.py:45`
- `src/pipeline/multi_video.py:50`
- `src/pipeline/multi_video.py:65`

问题：

第 5 轮已经在 `merge_clips_to_highlight()` 调用前后检查 `cancel_event`，这解决了“取消后仍进入 merge”以及“merge 后误标 completed”的问题。但 `merge_clips_to_highlight()` 内部的 join、audio mix、report 仍不接收 cancel token。用户如果在 FFmpeg join 或 audio mix 执行中取消，worker 只能等函数返回后才观察到 cancel。

影响：

- 长视频、多片段合并时，Dashboard 取消体验仍可能不及时。
- TaskManager 仍可通过进程终止兜底，但 worker 层无法优雅返回“取消于 join/audio/report 阶段”的结构化结果。

建议：

只在真实用户反馈取消体验差时再修，不建议马上展开大改。若要修，给 `merge_clips_to_highlight()` 增加可选 `cancel_event=None`，在 join 前、audio mix 前、report 前检查即可。不要为了这个问题重写 FFmpeg 执行层。

### P2-2：typed config view 的 bool 归一化对字符串过于宽松

位置：

- `src/config/detection_view.py:21`
- `src/config/detection_view.py:60`
- `src/config/detection_view.py:68`
- `src/config/detection_view.py:136`
- `src/config/validation.py:52`
- `src/config/validation.py:134`

问题：

`DetectionConfigView._as_bool()` 当前使用 `bool(value)`。这意味着字符串 `"false"`、`"0"` 都会被解析为 `True`。正式配置加载路径有 `validate_config()`，会要求 `detection.ocr.enabled` 和 rule `enabled` 是 boolean，因此已验证配置不容易触发该问题。但 typed view 已经开始承担 raw config/draft config 的兼容读取职责，而且测试也允许 threshold/weights 这类字段从字符串归一化为数值。

影响：

- Config Assistant 或未来 draft config 如果绕过严格校验，可能把 `"false"` 错读为启用。
- typed view 的“归一化”语义会变得不一致：数值字符串被认真解析，布尔字符串却按 Python truthy 处理。

建议：

小修即可：`_as_bool()` 只接受真实 bool；可选兼容 `"true" / "false" / "1" / "0"`，其他类型回落默认值。补 `tests/test_detection_config_view.py` 覆盖字符串布尔值。不需要引入 Pydantic 或更重的 schema 框架。

### P3-1：Config Assistant preview 与真实检测链路已复用核心判断，但单图信号采集仍有合理重复

位置：

- `src/tools/config_assistant/services/config_test_service.py:178`
- `src/tools/config_assistant/services/config_test_service.py:264`
- `src/tools/config_assistant/services/config_test_service.py:291`
- `src/ai/signal_extractors.py:148`
- `src/ai/detection_preview.py:18`

现状：

第 5 轮新增 `DetectionPreviewEvaluator` 后，rule merge、rule evaluation、weighted confidence 和 signal boolean 已经复用真实 detection 领域模型，这是正确方向。但 Config Assistant 仍保留自己的单图 color/template/OCR 细节采集逻辑，用于返回 UI 所需的 ROI、颜色命中率、模板列表、OCR 详情和 warnings。

判断：

这不是坏味道，不建议为了“完全复用”强行把它并入 `DetectionSignalExtractor`。真实检测链路需要高吞吐和简洁事件，Config Assistant 需要解释型详情，两者的输出目标不同。只要核心判断复用，保留 UI 详情采集是合理的。

建议：

后续只在出现实际不一致时补测试，不要继续抽一个更通用的 “SignalDetailExtractor”。

`VideoJoiner` 已从约 405 行降到 239 行，命令构造迁入 `JoinCommandBuilder`。这让 concat、xfade、normalize 的命令结构可以独立测试，是有价值的改动。

建议：

暂时停止继续拆分。只有在新增“NVENC 失败自动 fallback”“concat demuxer 快速路径”“软件编码策略矩阵”时，再按真实策略边界拆。
