## 高优先级问题

### P1：Dashboard worker 可能把失败 pipeline 标记为成功

证据：

- `src/tools/dashboard/task_manager.py:281` 多视频模式调用 `pipeline.run_until_clips(video_path)`，该方法异常时返回空列表，worker 没有记录单视频失败。
- `src/tools/dashboard/task_manager.py:283` 单视频模式调用 `pipeline.run(video_path)`，但没有检查返回值。
- `src/tools/dashboard/task_manager.py:336-337` 最终无条件写入 `"success": True`。

影响：

CLI 层已经能在失败时返回非零退出码，但 Dashboard 仍可能把失败任务展示为完成。对长耗时视频处理工具来说，这会直接误导用户，也会让前端下载区、历史记录或后续自动化拿到错误结果。

建议：

1. 单视频模式保存 `success = pipeline.run(video_path)`，失败时立即 `result_queue.put({"success": False, ...})`。
2. 多视频模式让 `run_until_clips()` 返回结构化结果，而不是只返回 clip list；至少包含 `success`、`error`、`stage_summary`。
3. Dashboard worker 汇总每个视频的状态：只要存在真正失败，任务结果应为 failed；“无击杀”应与“处理失败”区分。
4. 增加 dashboard worker 级测试：mock `Pipeline.run()` 返回 `False` 时，`TaskManager` 最终状态必须是 `FAILED`。

### P1：`run_until_clips()` 的 checkpoint/resume 契约不完整

证据：

- `src/pipeline/pipeline.py:454-457` `run()` 会设置 `_video_path` 和 `_fingerprints`。
- `src/pipeline/pipeline.py:521` `run_until_clips()` 单独实现 clips-only 流程，但没有设置 `_video_path` 和 `_fingerprints`。
- `src/pipeline/pipeline.py:473` 只有 `run()` 尝试 `_load_checkpoint(...)`。
- `src/pipeline/pipeline.py:547` `run_until_clips()` 调 `_run_plan(..., resume_completed=False)`，即使 checkpoint 文件存在也不会复用已完成阶段。

影响：

多视频模式会写 checkpoint，但 checkpoint 中的视频路径和配置 fingerprint 可能为空，且复跑时不会真正 resume。这会削弱长视频批处理的可恢复性，也会让 checkpoint 文件看起来存在但实际价值有限。

建议：

1. 抽出公共初始化函数，例如 `_prepare_run(video_path, checkpoint_path=None)`，供 `run()` 和 `run_until_clips()` 共用。
2. `run_until_clips()` 也应设置 `_video_path`、`_fingerprints`、checkpoint path，并执行 `_load_checkpoint()`。
3. clips-only 模式应只 resume 到 `clips` 阶段，但仍要做 config fingerprint invalidation 和 artifact validation。
4. 为 `run_until_clips()` 增加 checkpoint 内容测试：断言 `video_path` 非空、`fingerprints` 非空、第二次运行能跳过已完成 frames/detection。

### P1：Dashboard 进度仍是估算值，不是 Pipeline 的真实进度事件

证据：

- `src/tools/dashboard/task_manager.py:246` 注释明确是估算 detection progress。
- `src/tools/dashboard/task_manager.py:253` 使用 `elapsed * 100` 粗略估计帧处理数量。

影响：

GPU、CPU fallback、OCR subprocess、batch size、视频分辨率都会显著改变处理速度。估算进度在真实任务中容易卡住、跳变或提前满格，降低 Dashboard 对长任务的可信度。

建议：

1. 在 `run_detection_stage()` 或 progress bar 工厂中引入 progress callback。
2. PipelineContext 可携带 `event_sink`，stage 每处理 batch 后发送 `{stage, processed, total, detected}`。
3. Dashboard worker 只转发真实事件，不再自己轮询 Pipeline 内部状态和估算 FPS。

## 中优先级问题

### P2：Pipeline 类仍然是编排复杂度中心

`src/pipeline/pipeline.py` 已经比早期状态更好，但仍同时负责：

- stage 状态更新与 checkpoint 保存；
- checkpoint 加载、artifact 校验后的 invalidation；
- config fingerprint 计算和最早失效阶段判断；
- metadata/frames/detection/clips 的前半段流程；
- join/audio/report/history/cleanup 的后半段流程；
- 性能报告保存；
- `run()` 与 `run_until_clips()` 两套入口。

建议：

1. 新增 `PipelineRunner`：只负责按 plan 执行 stage。
2. 新增 `RunInitializer` 或 `_prepare_run()`：统一 video path、checkpoint path、fingerprint、resume 初始化。
3. 让 `Pipeline` 变成 facade：暴露 `run()`、`run_until_clips()`，内部委托 runner。
4. 将性能报告保存挪到独立 stage 或 post-run hook，避免主流程继续膨胀。

### P2：Pipeline result contract 还没有完全落地

证据：

- `src/pipeline/results.py` 已定义 `PipelineResult`、`StageResult` 和 result key 校验。
- 但 `src/pipeline/pipeline.py` 仍以 `self.results: Dict[str, Any] = {}` 作为主存储。
- 只有 stage 返回值经过 `StageResult` 校验，直接写入 `self.results[...]` 的地方仍绕过统一对象。

影响：

结果 key 常量已经存在，但编译期和运行期保护还不完整。后续新增 stage 或 dashboard 消费字段时，仍可能出现拼写错误、空值语义不一致、历史 checkpoint 兼容困难。

建议：

1. `Pipeline.results` 改为 `PipelineResult` 或轻量 `ArtifactStore`，对外提供 `get/set/update/as_dict`。
2. checkpoint save/load 只接收合法 result key。
3. 对 optional artifact 明确语义：`None`、缺 key、空列表分别代表什么。

### P2：FFmpeg/FFprobe 路径配置没有全链路统一

证据：

- `config/default_config.yaml` 定义了 `video.ffmpeg_path` 和 `video.ffprobe_path`。
- `src/audio/audio_mixer.py:11` 构造函数默认 `ffmpeg_path="ffmpeg"`，`run_audio_stage()` 调用 `AudioMixer(context.config)` 时没有传入配置里的 `ffmpeg_path`。
- `src/video/frame_extractor.py:193` precise fallback 仍硬编码 `"ffprobe"`。
- `src/video/video_info.py:34` 和 `src/audio/audio_info.py:41` 也直接调用 `'ffprobe'`。

影响：

用户配置自定义 FFmpeg/FFprobe 路径后，部分链路仍会走系统 PATH。Windows 环境下这很容易导致 CLI 主流程可用，但 dashboard、audio、metadata 或 fallback 路径失败。

建议：

1. 所有 FFmpeg/FFprobe 使用统一 `FFmpegTools` 或 `VideoToolConfig` 对象。
2. `VideoInfo`、`AudioInfo` 支持传入 `ffprobe_path`，调用方必须从 config 传递。
3. `AudioMixer` 默认从 config 读取 `ffmpeg_path`，而不是依赖构造参数默认值。
4. 增加测试：设置 `video.ffprobe_path="custom_ffprobe"`，mock subprocess 断言所有相关模块使用该路径。

### P2：Config schema 仍是 loose dict，类型契约不够强

当前 `src/config/validation.py` 已有基础校验，但主链路仍大量使用 `config.get("...")` 和嵌套 dict。随着 detection rules、template overrides、join_fix、audio、dashboard 配置继续增长，dict 契约会越来越难维护。

建议：

1. 先引入 dataclass 层，不一定立即引入 Pydantic。
2. 典型对象包括 `VideoConfig`、`DetectionConfig`、`OCRConfig`、`PrefilterConfig`、`JoinFixConfig`、`HighlightConfig`。
3. YAML load 后先转换成 typed settings，业务代码只读 settings，不直接读原始 dict。
4. 保留原始 dict 给 report/debug 输出，但不要作为内部主契约。

### P2：测试 lint 仍依赖大量整文件 ignore

证据：

- `pyproject.toml:9` 开始配置 per-file ignores。
- `pyproject.toml:11-28` 对多份测试文件整文件忽略 `E/F/B`。

影响：

当前 `ruff check .` 通过，但一部分测试代码没有受到有效约束。测试本身是长期维护资产，过多整文件 ignore 会掩盖未使用 fixture、错误 mock、宽泛异常和未来迁移问题。

建议：

1. 保留 `scripts/debug/*.py` 和 `tests/manual/*.py` 的宽松策略。
2. 对普通单元测试逐个移除整文件 ignore。
3. 对确实需要特殊处理的行使用局部 `# noqa: CODE`。
4. 将目标设为 `tests/` 普通测试目录同样通过 `E/F/B`。

### P2：Config Assistant API 单文件过大

`src/tools/config_assistant/api.py` 约 898 行，包含上传、游戏列表、ROI、OCR、模板、颜色、规则、legacy endpoint、图像裁剪和预览等逻辑。虽然已有 `services/config_test_service.py`，但 API 文件仍承担过多职责。

建议拆分：

- `routes/config_routes.py`
- `routes/template_routes.py`
- `routes/color_routes.py`
- `routes/rule_routes.py`
- `services/image_service.py`
- `services/config_writer.py`

拆分时优先保证 endpoint 行为不变，先搬迁纯函数和重复校验逻辑。

### P2：KillDetector 仍可继续瘦身

当前信号抽取和融合已经拆出，但 `KillDetector` 仍包含规则配置 merge、规则信号重算、单帧流程、batch 流程、事件构造和 profiler 记录。

建议：

1. 将 rules 相关逻辑独立为 `DetectionRuleEngine`。
2. 将 batch 候选帧流程独立为 `BatchDetectionRunner`。
3. `KillDetector` 只保留三件事：prefilter、precise detect、返回 event/result。

## 低优先级问题

1. `src/ai/model_manager.py:33` 注释说明 YOLO 缺模型会自动下载。项目定位是 offline-only，本行为应变成显式开关，例如 `ai.allow_model_download`，默认运行期关闭。
2. 多处还有 `except Exception: pass` 或宽泛捕获，常见于 OCR cleanup、dashboard queue、frame fallback、临时文件清理。清理类场景可以保留，但需要尽量记录 debug 日志。
3. `src/video/video_joiner.py` 的 FFmpeg filter 字符串构建较复杂，建议为 concat/xfade/anullsrc 分别补充 snapshot 级命令构建测试。
4. `BatchProcessor._process_multi_video()` 用 `len(clips) > 0 or clips stage SKIPPED` 判断 success，异常返回空 clips 时可能和“无击杀”混淆，建议依赖结构化 result。
5. 中英文注释混用较多。项目面向中文使用者可以接受，但建议核心库代码统一注释语言，UI 文案另行管理。

## 架构建议

### 1. 统一运行结果模型

建议定义：

```python
@dataclass
class PipelineRunResult:
    success: bool
    mode: str
    video_path: str
    clips: list[dict]
    final_video: str | None
    report_path: str | None
    failed_stage: str | None
    error: str | None
```

`Pipeline.run()` 和 `Pipeline.run_until_clips()` 都返回该对象。CLI、BatchProcessor、Dashboard 都只消费这个对象，避免每层自己推断成功或失败。

### 2. 引入真实 progress event

推荐最小实现：

```python
class ProgressSink(Protocol):
    def emit(self, event: dict) -> None:
        ...
```

`PipelineContext` 持有 `progress_sink`，stage 内部发送真实进度。CLI 可以适配 rich progress，Dashboard 可以转发 queue，测试可以收集事件断言顺序。

### 3. 让 checkpoint 和 artifact 契约成为 stage metadata

当前 `ArtifactValidator` 手写 stage 到 result key 的映射。下一步可以把 stage 定义改成：

```python
@dataclass(frozen=True)
class StageSpec:
    name: str
    result_keys: tuple[str, ...]
    artifact_validator: Callable[[dict], bool]
```

这样新增 stage 时不会忘记更新 checkpoint、invalidation、artifact cleanup 三套映射。

### 4. 类型化配置入口

短期可以保留 YAML 和 dict，但建议业务层读取 typed settings：

```python
settings = AppSettings.from_dict(config)
Pipeline(settings)
```

这会显著减少 `config.get(...).get(...)` 的重复和默认值漂移，也能让 IDE、测试和 review 更容易发现配置字段未生效。

## 建议整改路线

### 第一阶段：可靠性一致性

1. 修 Dashboard worker：检查 `pipeline.run()` 返回值，失败时输出 failed result。
2. 将 `run_until_clips()` 改为共享 `run()` 的初始化和 checkpoint resume 逻辑。
3. 为 clips-only 失败、无击杀、成功提取 clips 三种情况建立结构化返回。
4. 增加 Dashboard worker 和 BatchProcessor 的失败语义测试。

### 第二阶段：配置和工具链一致性

1. 统一 FFmpeg/FFprobe path 注入。
2. 给 `VideoInfo`、`AudioInfo`、`AudioMixer`、FrameExtractor fallback 补齐配置路径测试。
3. 将模型自动下载策略改为显式配置。

### 第三阶段：复杂度收敛

1. 抽 `PipelineRunner` 和 progress event。
2. 抽 `DetectionRuleEngine` 与 `BatchDetectionRunner`。
3. 拆 `config_assistant/api.py` 的 routes/services。
4. 逐步移除普通测试文件的整文件 lint ignore。

## 推荐质量门禁

建议把以下命令作为本地 preflight 和 CI 基线：

```powershell
.venv\Scripts\python.exe -m ruff check . --statistics
.venv\Scripts\python.exe -m pytest tests/ -q
.venv\Scripts\python.exe -m compileall -q src main.py scripts
```

对于涉及 FFmpeg、GPU、OCR subprocess、Dashboard worker 的改动，建议额外跑对应 focused tests，并尽量用 mock subprocess 验证命令参数，而不是依赖真实大视频素材。

## 最终评价

当前仓库已经过了“能跑就行”的阶段，核心工程骨架是成立的：有配置、有测试、有 stage、有 checkpoint、有 dashboard，也开始把 AI 信号和 pipeline artifact 抽象出来。

下一步最值得投入的不是继续加新功能，而是把运行契约做硬：Pipeline 返回结构化结果，Dashboard 不自行猜测成功失败，progress 来自真实 stage event，FFmpeg/FFprobe 配置全链路一致。完成这些后，项目会更接近一个可长期维护和稳定发布的本地视频处理工具。
