## 高优先级问题

### P0：`setup.py` 打包配置当前不可用

证据：

- `setup.py:6` 使用 `packages=find_packages()`。
- 当前仓库源码在 `src/` 目录下，但没有标准 `src` package 根声明，也没有 `package_dir` 配置。
- 实测 `.venv\Scripts\python.exe -c "from setuptools import find_packages; print(find_packages())"` 返回 `[]`。
- `setup.py:29` console entry point 指向 `fpsvideosnap=main:main`，但 `main.py` 位于仓库根目录，不是可安装 package 模块。

影响：

- `pip install .` 基本不会安装业务包。
- console script 入口不可靠。
- 当前能运行主要依赖“在仓库根目录执行 `python main.py` + `main.py` 手动 `sys.path.append(...)`”。
- 后续 CI、发布、用户安装、Dashboard 子进程运行路径都会继续依赖当前目录布局。

建议：

1. 短期修复 `setup.py`：

   ```python
   setup(
       packages=find_packages(where=".") + ["src"],
       py_modules=["main"],
       include_package_data=True,
   )
   ```

   这只是过渡方案，不是最终推荐。

2. 推荐迁移到标准包结构：

   ```text
   src/
     fpsvideosnap/
       __init__.py
       __main__.py
       cli.py
       ai/
       pipeline/
       ...
   ```

3. 在 `pyproject.toml` 中定义：

   ```toml
   [project.scripts]
   fpsvideosnap = "fpsvideosnap.__main__:main"
   ```

4. 增加安装 smoke test：

   ```powershell
   .venv\Scripts\python.exe -m pip install -e .
   .venv\Scripts\python.exe -c "import src.pipeline.pipeline"
   fpsvideosnap --help
   ```

### P1：ruff 当前通过依赖大量 per-file-ignore

证据：

- `pyproject.toml` 对大量 `src/` 和 `tests/` 文件关闭了 `E`、`F`、`B`。
- 标准配置下 ruff 通过。
- 脱离 per-file-ignore 后，`ruff --isolated --select E,F,B --statistics` 发现 546 个问题，包括：
  - 438 个 `E501 line-too-long`
  - 53 个 `F401 unused-import`
  - 15 个 `F841 unused-variable`
  - 9 个 `B023 function-uses-loop-variable`
  - 7 个 `B904 raise-without-from-inside-except`
  - 2 个 `E722 bare-except`

影响：

- 当前 lint 更像“新文件局部门禁”，还不是全仓质量门禁。
- `F401`、`F841`、`B023`、`B904` 这类问题不是纯格式问题，可能隐藏真实 bug。
- 未来重构核心模块时，自动保护力度不足。

建议：

1. 分三批收敛，不要一次全修：
   - 第一批：`F401`、`F841`、`E722`、`B904`。
   - 第二批：`B023`、`B006`、`E701`。
   - 第三批：`E501`，先核心代码后测试。
2. 每完成一个模块，从 `per-file-ignores` 中移除该模块。
3. 优先解除这些文件的忽略：
   - `src/pipeline/pipeline.py`
   - `src/pipeline/stages/detection_stage.py`
   - `src/ai/kill_detector.py`
   - `src/config/config_loader.py`
   - `src/video/*.py`

### P1：`Pipeline` 后半段仍是厚编排层

证据：

- `src/pipeline/pipeline.py` 仍约 28KB。
- `run()` 中仍直接处理 join、audio、report、history、cleanup、performance profile 保存。
- `_run_to_stage()` 只覆盖到 clips，后半段没有统一 stage runner。
- 失败时 `run()` 捕获 `Exception` 后返回 `False`，但当前 running stage 不一定被标记为 `FAILED`。

影响：

- join/audio/report/history 的 resume、重建、失败状态和结果字段继续耦合。
- 多视频模式与单视频模式仍有分叉，`BatchProcessor` 自己做了一套 merge/audio/report。
- Dashboard 很难获得可靠的阶段事件，只能通过线程估算进度。

建议：

1. 把后半段继续拆成 stage：
   - `JoinStage`
   - `AudioStage`
   - `ReportStage`
   - `HistoryStage`
   - `CleanupStage`
2. 用一个统一的 `StageRunner` 执行 stage plan：

   ```python
   full_plan = ["metadata", "frames", "detection", "clips", "join", "audio", "report", "history", "cleanup"]
   clips_plan = ["metadata", "frames", "detection", "clips"]
   ```

3. stage 返回结构化结果，而不是直接写裸 dict。
4. 任意 stage 失败时设置 `StageStatus.FAILED`，保存 checkpoint，并向 Dashboard 暴露失败阶段与错误原因。

### P1：Config Assistant API 与运行时检测逻辑重复

证据：

- `src/tools/config_assistant/api.py` 约 47KB，是当前最大 Python 文件。
- 文件内重复实现了 `_get_color_bounds()`、`_merge_detection_config()`、OCR keyword matching、weighted confidence、rules test 等逻辑。
- `KillDetector` 中也有对应逻辑。

影响：

- 配置助手的“测试图片结果”可能与真实 pipeline 检测结果漂移。
- 规则、颜色、模板阈值逻辑新增字段时，需要同时修改 API 和运行时检测模块。
- API 文件同时承担路由、输入校验、图像处理、规则评估、配置保存，单测成本高。

建议：

1. 抽出共享服务层：

   ```text
   src/ai/color_utils.py
   src/ai/rule_evaluator.py
   src/ai/signal_evaluator.py
   src/tools/config_assistant/services/config_test_service.py
   ```

2. Config Assistant API 只做：
   - request 解析
   - 文件保存
   - 调用 service
   - response 序列化
3. 配置测试端点与 `KillDetector` 共用同一套颜色边界、规则评估和信号布尔化逻辑。
4. 把 legacy endpoints 单独放到 `legacy_api.py`，降低主 API 文件复杂度。

### P1：Web 上传与路径 API 需要加固

证据：

- `src/tools/config_assistant/api.py:335` 使用 `os.path.join(upload_folder, file.filename)`。
- `src/tools/config_assistant/api.py:336` 直接 `file.save(filepath)`。
- `src/tools/config_assistant/server.py` 未设置 `MAX_CONTENT_LENGTH`。
- `src/tools/dashboard/api.py` 的 `/scan` 接收任意本地目录路径并枚举视频文件。

影响：

- Config Assistant 虽然只绑定 `127.0.0.1`，但仍应把上传文件名和上传大小作为边界处理。
- 任意路径扫描对本机可信工具可以接受，但应有明确的安全约束和测试。
- 上传文件若带路径分隔或特殊文件名，可能造成不可预期路径行为。

建议：

1. 上传统一使用 `sanitize_filename()` 和 `safe_join()`：

   ```python
   safe_name = sanitize_filename(file.filename)
   filepath = safe_join(upload_folder, safe_name)
   file.save(filepath)
   ```

2. 设置上传大小上限：

   ```python
   app.config["MAX_CONTENT_LENGTH"] = 20 * 1024 * 1024
   ```

3. 为上传路径穿越、超大文件、非法扩展名补测试。
4. Dashboard `/scan` 至少记录本机可信假设，并考虑限制到用户显式选择的目录或增加 allowlist 配置。

### P2：领域数据模型仍偏弱

现状：

- `DetectionEvent`、clip metadata、pipeline results、config dict 基本仍是裸 `dict`。
- `SignalResult` 已存在，但 `details` 字段没有在 `as_dict()` 中输出。
- `DetectionStageResult` 已存在，但后续 stage 没有对应 result 类型。

影响：

- 字段契约依赖测试和约定，不利于长期演进。
- JSON 持久化边界和内存对象边界没有清晰分层。
- 毫秒、秒、路径、置信度字段容易混用。

建议：

1. 增加核心模型：

   ```text
   DetectionEvent
   ClipMetadata
   PipelineResult
   StageResult
   ```

2. 统一提供 `to_dict()` / `from_dict()`，确保历史记录和 report 不受内部模型变化影响。
3. 先从 `DetectionEvent` 和 `ClipMetadata` 开始，风险最低、收益最高。

## 架构评价

### 优点

- 目录按领域划分清晰：`ai`、`video`、`clip`、`audio`、`config`、`pipeline`、`tools`、`report`。
- OCR 子进程隔离符合 Windows + PaddleOCR + PyTorch 的真实工程约束。
- `FrameExtractor` 有 bulk + precise fallback，兼顾性能和时间戳可靠性。
- `Pipeline` 已有 checkpoint、fingerprint、resume、history、debug visual、performance profile。
- 测试速度快，适合频繁回归。
- 静态资源离线化和仓库完整性测试已经补上。

### 主要架构债

- `Pipeline` 仍是半拆分状态，后半段 stage 化不足。
- `KillDetector` 仍同时承担信号提取、规则覆盖、置信度、批处理和缓存判断。
- Config Assistant API 过大，路由层和领域逻辑没有分离。
- 全局单例仍偏多：`temp_manager`、全局 profiler、OCR service、Dashboard task manager。
- 打包结构不标准，当前仓库更像脚本项目而不是可安装应用。

## 代码质量评价

### 类型与契约

当前类型标注比早期更好，但很多接口仍是 `Dict[str, Any]`。建议把“运行时核心字段”优先结构化，而不是对所有配置一次性上强类型。

优先级：

1. `DetectionEvent`
2. `ClipMetadata`
3. `PipelineStageResult`
4. `ValidatedConfig`

### 异常处理

已有一些具体异常处理，例如 frame timestamp 解析捕获 `IndexError` / `ValueError`。但仍存在较多 `except Exception` 和少量裸 `except`，其中资源清理类可以接受，但业务流程类应更具体。

建议：

- stage 内部失败抛出带上下文的自定义异常。
- `Pipeline.run()` 统一捕获并设置失败阶段。
- 清理失败用 warning/debug log，不影响主流程。

### 资源管理

`DetectionStage` 已在 `finally` 中关闭 OCR 资源，这是好改进。仍需关注：

- `temp_manager.clean_all()` 是全局清理，Dashboard 多任务或未来并发时风险较高。
- 全局 profiler 不按 run 隔离，连续任务统计可能互相污染。
- Dashboard cancel 使用 `terminate()` / `kill()`，需要保证子进程中的 FFmpeg、OCR 子进程和临时文件被处理。

建议：

- 每次 pipeline run 拥有独立 `RunContext`，其中包含 temp manager 和 profiler。
- `Pipeline` 析构或 cleanup 只清理自己创建的路径。
- Dashboard cancel 增加子进程树清理测试。
