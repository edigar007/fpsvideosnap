## 高优先级问题

### 1. `src/history` 源码被 `.gitignore` 误忽略，干净环境会缺模块

严重级别：**P0 / 交付阻断风险**

证据：

- `src/pipeline/pipeline.py:24` 引入 `from src.history.history_manager import HistoryManager`
- `tests/test_report.py:7` 也引入 `HistoryManager`
- 本地磁盘存在 `src/history/history_manager.py`，但 `git ls-files src/history` 无输出
- `git check-ignore -v src\history\history_manager.py` 命中 `.gitignore:36 history/`

影响：

- 当前机器测试可过，是因为本地有被忽略的源码文件。
- 干净 clone、CI、其他开发者机器、打包发布都会出现 `ModuleNotFoundError: No module named 'src.history'`。

建议：

- 将 `.gitignore` 中 `history/` 改成 `/history/`，只忽略项目根目录运行历史。
- 将 `src/history/__init__.py` 和 `src/history/history_manager.py` 纳入版本控制。
- 增加一次干净 checkout 或 `git clean -xfd` 等价环境的导入检查到 CI。

### 2. Config Assistant 使用外部 CDN，违反离线本地工具约束

严重级别：**P1 / 架构约束不一致**

证据：

- `src/tools/config_assistant/static/index.html:9` 加载 `https://cdnjs.cloudflare.com/.../font-awesome...`
- `src/tools/config_assistant/static/index.html:10` 加载 `https://fonts.googleapis.com/...`
- 项目规则要求本地工具不使用云 API 或网络请求，模型初始下载除外。

影响：

- 离线环境下图标/字体退化。
- 内网或无外网机器体验不可控。
- 安全审计时会被视为主动依赖外部网络资源。

建议：

- 将 Font Awesome 或替代图标资源 vendoring 到 `src/tools/config_assistant/static/vendor/`。
- 使用本地字体或系统字体栈。
- 增加静态资源扫描测试，禁止 `http://`、`https://` 外部资源出现在运行时 HTML/CSS/JS 中。

### 3. `Pipeline` 文件承担过多职责，已经成为维护瓶颈

严重级别：**P1 / 长期维护风险**

证据：

- `src/pipeline/pipeline.py` 约 40KB，含阶段状态、checkpoint、fingerprint、帧读取、检测循环、debug 视频、剪辑、拼接、音频、报告、历史、清理。
- `Pipeline.run()` 从 `src/pipeline/pipeline.py:226` 开始，覆盖完整端到端流程。
- `Pipeline.run_until_clips()` 从 `src/pipeline/pipeline.py:638` 开始，与 `run()` 中的 metadata、frame extraction、detection、clip extraction 逻辑大量重复。

影响：

- 新增阶段或改动检测流程时，容易破坏 resume、多视频模式、debug 和清理逻辑。
- 进度监控、异常恢复、资源释放和结果结构互相耦合。
- 测试只能大量 mock 大对象，难以做窄范围单元测试。

建议：

- 抽出阶段类或阶段函数：`MetadataStage`、`FrameExtractionStage`、`DetectionStage`、`ClipStage`、`JoinStage`、`AudioStage`、`ReportStage`。
- 让 `run()` 和 `run_until_clips()` 复用同一组 stage runner，通过目标阶段或 stage plan 控制停止点。
- 将 checkpoint/resume 与实际处理逻辑分离成 `CheckpointStore` 或 `PipelineStateStore`。

### 4. 检测规则、信号计算和配置覆盖混在 `KillDetector` 中，规则模式可能重复计算重型信号

严重级别：**P1 / 性能与可维护性风险**

证据：

- `src/ai/kill_detector.py:13` 的 `KillDetector` 同时负责 OCR 初始化、预过滤、颜色检测、模板匹配、YOLO 信号、规则覆盖、规则求值和批处理。
- `src/ai/kill_detector.py:355` `_evaluate_rules()` 对每条 rule 调用 `_compute_rule_signals()`。
- `src/ai/kill_detector.py:500` `_process_candidates_sequential()` 已经调用 `_precise_detect()`，随后规则模式又调用 `_evaluate_rules()`，规则覆盖存在时可能重复 OCR/模板/颜色逻辑。

影响：

- 规则越多，候选帧越多，OCR 和模板匹配成本越高。
- 同一帧的信号结果和“规则有效配置”之间缺少明确缓存协议。
- 后续增加新信号时，需要同时改多个私有方法。

建议：

- 引入 `SignalExtractor`，输出结构化信号结果和 per-signal detail。
- 引入 `RuleEvaluator`，只消费信号和规则配置，不直接调用 OCR/YOLO/OpenCV。
- 对 per-rule override 的信号计算做缓存：按 `(frame_id, effective_config_fingerprint)` 缓存。
- 把 legacy weighted mode 和 rules mode 明确拆成两个策略类。

### 5. 依赖定义不一致，安装和打包路径不可靠

严重级别：**P1 / 环境复现风险**

证据：

- `requirements.txt` 包含 `paddleocr==3.3.2`、`easyocr`、`python-Levenshtein`、CUDA 版 torch 等。
- `setup.py` 未包含 `paddleocr`、`easyocr`、`python-Levenshtein`，且 entry point 指向 `fpsvideosnap=main:main`。
- `main.py:31` 使用 `sys.path.append(...)`，说明包导入方式仍依赖源码目录布局。

影响：

- `pip install .` 和 `pip install -r requirements.txt` 得到的运行环境不同。
- 控制台入口可能在打包安装后找不到根目录 `main.py` 或配置文件。
- 依赖升级风险高，尤其是 PyTorch/PaddleOCR/Ultralytics/OpenCV 的组合。

建议：

- 迁移到 `pyproject.toml`，定义 `project.optional-dependencies`：`gpu`、`ocr-paddle`、`ocr-easy`、`dev`。
- 将入口函数放到包内，例如 `src/fpsvideosnap/__main__.py` 或 `src/cli_app.py`。
- 固定高风险依赖版本区间，并记录 Windows CUDA/PaddleOCR 兼容矩阵。

## 架构评价

### 优点

- 目录分层基本合理：`src/ai`、`src/video`、`src/clip`、`src/audio`、`src/config`、`src/pipeline`、`src/tools` 的领域边界清晰。
- 配置驱动意识较强，游戏差异主要通过 `config/games/*.yaml` 管理。
- OCR 使用子进程隔离 PaddleOCR 与 PyTorch GPU DLL 冲突，是符合 Windows 实际约束的务实设计。
- `FrameExtractor` 支持 bulk + fallback precise，兼顾性能和时间戳准确性。
- Checkpoint、config fingerprint、history、debug visual、performance profiler 说明项目已经开始考虑长期运行体验。
- 测试数量充足，本地全量测试速度快，适合持续迭代。

### 主要架构债

- 编排层过厚：`Pipeline` 不只是编排，还直接做大量业务细节和文件系统操作。
- 领域模型偏弱：事件、clip、信号、规则、阶段结果多以裸 dict 表示，字段契约散落在代码和测试中。
- Web 工具和核心处理共享源码但边界不清：Config Assistant API 中复制了检测信号逻辑，容易与 `KillDetector` 行为漂移。
- 全局单例较多：`temp_manager`、全局 `profiler`、OCR subprocess singleton 会让多任务、测试隔离和 Dashboard 并发更复杂。
- 配置 schema 只做局部校验，没有统一 schema/version/migration 机制。

## 代码质量观察

### 类型与数据契约

当前大量函数返回 `Dict[str, Any]` 或裸 dict，例如 detection event、clip metadata、pipeline results。短期能快，但字段增长后会降低可维护性。

建议：

- 用 `dataclass` 或 `TypedDict` 定义 `DetectionEvent`、`SignalResult`、`ClipMetadata`、`PipelineResult`。
- 对 JSON 持久化边界提供 `to_dict()` / `from_dict()`。
- 将 `timestamp_ms`、`start_ms`、`end_ms` 统一为强约定字段，避免秒/毫秒混用。

### 异常处理

存在裸 `except` 和吞异常：

- `src/pipeline/pipeline.py:363`
- `src/pipeline/pipeline.py:732`
- 多处 `except Exception: pass` 用于资源释放和清理

建议：

- 时间戳解析应捕获 `IndexError`、`ValueError`，并记录文件名。
- 资源清理可以吞异常，但至少用 debug log 留痕。
- 流水线阶段失败时建议设置当前 stage 为 `FAILED`，而不是只返回 `False`，便于 Dashboard 和 checkpoint 判断。

### 魔法常量

例子：

- `src/pipeline/pipeline.py:346` 和 `src/pipeline/pipeline.py:716` 固定 `chunk_size = 256`
- 模板默认阈值 `0.8`
- Dashboard 检测进度估算固定 “100 frames per second”

建议：

- 放入 `config/default_config.yaml`：`detection.chunk_size`、`detection.template_default_threshold`、`dashboard.progress_estimated_fps`。
- CLI 或 config assistant 展示这些配置，避免性能调参要改源码。

### 重复逻辑

- `Pipeline.run()` 和 `Pipeline.run_until_clips()` 重复了 metadata、frame extraction、detection、clip extraction。
- Config Assistant API 中 `_get_color_bounds()`、规则合并、权重计算等逻辑与 `KillDetector` 重复。
- 不同模块各自解析/拼接路径，缺少统一 project paths。

建议：

- 建立 `src/detection/` 或 `src/ai/signals.py` 共享信号计算/规则求值。
- 建立 `src/pipeline/stages.py` 复用阶段实现。
- 建立 `ProjectPaths` 或 `AppContext`，集中处理 root/config/models/temp/history/output。

## 工程化与仓库治理

### 版本控制

当前最大问题是 `.gitignore` 的 `history/` 会匹配任意路径下的 `history` 目录，导致 `src/history` 被忽略。应立即修正。

建议 `.gitignore` 调整：

```gitignore
/history/
/output/
/temp/
```

并确认源码目录不再被忽略：

```powershell
git check-ignore -v src\history\history_manager.py
```

预期应无输出。

### CI 与质量门禁

当前仓库未看到统一 lint/type 工具配置。

建议分阶段增加：

1. `ruff`：先启用基础规则，如 unused imports、bare except、undefined name。
2. `pytest`：保持当前全量测试。
3. `pyright` 或 `mypy`：先只检查新写模块或核心 dataclass。
4. 静态资源扫描：禁止运行时 HTML/CSS/JS 外部 URL。
5. 干净安装检查：`pip install -e .` 后执行 `python -c "import src.pipeline.pipeline"`。

### 依赖管理

建议拆分依赖：

- `requirements.txt`：最小运行依赖。
- `requirements-dev.txt`：pytest、ruff、类型工具。
- `requirements-win-gpu.txt`：CUDA/PyTorch/Ultralytics。
- `requirements-ocr-paddle.txt`：PaddleOCR 专用隔离环境。

更长期建议使用 `pyproject.toml` + optional dependencies，避免 `setup.py` 与 requirements 分叉。

## 配置系统评价

优点：

- `ConfigLoader` 支持 default + game + override 合并。
- `DETECTION_REPLACE_PATHS` 能避免某些 detection 子树被错误深合并。
- 规则校验覆盖了 name、enabled、require、信号枚举。

风险：

- 校验仍偏浅，未统一验证 ROI 范围、HSV 范围、模板路径、时间窗口、音量范围。
- `detection.batch_size` 和 `ai.batch_size` 存在语义重叠风险；`Pipeline` 当前读取 `ai.batch_size`，默认配置中 detection 下也有 `batch_size`。
- 配置版本缺失，未来新增字段或迁移旧 game config 会困难。

建议：

- 引入配置 schema，例如 Pydantic、jsonschema，或轻量 dataclass validator。
- 增加 `config_version`。
- 建立 `fpsvideosnap config validate --game ...` 命令。
- 将 Config Assistant 保存前校验与运行时校验复用同一套 schema。

## 安全与本地化

优点：

- Flask 服务默认绑定 `127.0.0.1`，比暴露 `0.0.0.0` 更稳妥。
- FFmpeg 调用使用参数数组，没有明显 shell injection。
- Dashboard 任务使用进程隔离，方向正确。

风险：

- Config Assistant/Dashboard 可访问用户提供的本地路径，应明确只用于本机可信用户。
- Config Assistant 上传文件应继续限制扩展名和大小，目前只看到扩展名限制。
- 外部 CDN 资源与离线要求冲突。

建议：

- 给 Flask 设置上传大小上限：`MAX_CONTENT_LENGTH`。
- 对路径扫描 API 增加清晰的本机信任边界说明。
- 所有前端资源本地化。

## 最终评价

这是一个功能推进很快、实用性方向明确的仓库。核心问题不是“能不能跑”，而是“能否在干净环境、离线环境、多人协作和长期迭代中稳定交付”。当前最需要先处理的是版本控制误忽略源码和离线资源违规；随后应把 `Pipeline` 与 `KillDetector` 拆成更小的可测试单元。

如果完成上述 P0/P1 项，综合评分可以较快提升到 **8.0+**。如果继续补齐配置 schema、依赖治理和阶段化架构，项目会进入更可靠的产品化状态。
